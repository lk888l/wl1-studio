# GameBox 游戏机接入

GameBox 是产品首页中的独立工作台，提供真实串口按键诊断、八键可视化、事件日志、六款游戏与六项工具图鉴，以及通过内置 probe-rs / ST-Link 的固件烧录和完整 Flash 读取。“存储与检查”保留本地 `.bin` 检查与分区说明。串口保持只读；烧录与读取使用独立 SWD 通道。游戏在 STM32 设备上运行，图鉴不启动或遥控游戏，ADC 波形和 I²C 扫描结果也没有串口回传。

桌面应用可使用真实串口；浏览器中的体验演示使用生成的按键事件，并明确标记无硬件。代码与构建均在本仓库内完成，`STM-GameBox` 仅是核对协议的源码来源，无需克隆或编译该外部仓库即可构建上位机。

## 串口接线与使用

1. 使用与板上 **3.3 V 逻辑电平**匹配的 USB-UART，将游戏机 **PA9 TX 接适配器 RX**，双方 **GND 共地**。当前诊断只需 TX 与 GND，供电按现有板卡方案处理。
2. 打开产品首页中的 GameBox 工作台，刷新并选择串口，主动连接。固定参数为 **115200 baud、8N1、无流控**。
3. 按游戏机上的实体按键，观察八键状态、事件类型、设备毫秒计时和保持时长；日志保留未识别文本，便于诊断接错端口或固件差异。
4. 如果需要确认启动标识，在串口连接后复位游戏机。启动行仅发送一次，中途连接可能错过；打开端口不能代表已经识别产品。
5. 结束时断开连接，再返回产品首页。换产品或重连后，旧会话事件不应影响当前工作台。

上位机不会自动发送探测、控制、刷写或校时命令。游戏机没有周期心跳：长时间没有按键事件不表示掉线；操作系统报告的端口故障与“没有新事件”是不同状态。

## 当前文本协议

设备启动时发送以下精确 ASCII 文本，以 CRLF 结束：

```text
GAMEBOX FW2 UART-TX-DMA READY\r\n
```

按键事件格式为：

```text
BTN <ms> <key> <event> <held_ms>\r\n
BTN 1200 UP PRESSED 0\r\n
BTN 1300 UP RELEASED 100\r\n
```

示例中的 `\r\n` 表示实际回车换行字节，不是四个可见字符。

| 字段 | 范围或含义 |
|---|---|
| `ms` | 设备单调毫秒计时，十进制 `u32`，可回绕；不是 RTC 时间或主机时间 |
| `key` | `UP`、`DOWN`、`LEFT`、`RIGHT`、`JUMP`、`FUNC`、`ENTER`、`BACK` |
| `event` | `PRESSED`、`RELEASED`、`CLICK`、`DOUBLE`、`LONG`、`REPEAT` |
| `held_ms` | 该事件携带的保持时间，十进制 `u32` |

启动行只提供兼容标记 `FW2`，没有硬件序列号、应用版本、屏幕接口或能力列表。匹配标记不是设备身份认证。按键行可用于观察事件，但不能补全中途连接前的状态，也不能可靠重建设备当前菜单、游戏分数或 OLED 画面。固件队列可能丢事件，日志统计不等同于完整的物理按键可靠性测试。

## ST-Link 烧录与完整 Flash 读取

进入 **GameBox → 固件与 Flash**。目标固定为暂定的 **STM32F103C8T6 / 64 KiB**，使用 probe-rs 内置 `STM32F103C8Tx` 目标及 F1 Flash 算法。桌面程序直接包含烧录引擎和芯片定义，复用 [USB 驱动与权限设置](wl1-firmware.md#首次-usb-设置无需另行下载)，无需另行下载烧录工具。

1. 断开游戏机串口或演示会话，保持板卡供电，将 ST-Link 接到 GND、PA13（SWDIO）、PA14（SWCLK）及目标参考电压，使用 3.3 V 电平。
2. 刷新并选择 ST-Link，默认 SWD 为 1000 kHz。连接失败时可降速，或连接 NRST 后选择“复位下连接”。
3. 烧录：选择 `.bin`、Intel `.hex`、32 位 ARM 小端 `.elf/.axf`。BIN 默认从 `0x08000000` 写入；HEX/ELF 使用文件中的加载地址。核对文件 SHA-256 和写入范围后确认，完成写入及回读校验后自动复位运行。
4. 读取：点击“读取全部 Flash”，读取 `0x08000000`–`0x0800FFFF` 的完整 **64 KiB**，包括末尾设置区；支持十六进制/ASCII 浏览、地址跳转、SHA-256 和 BIN 导出。

沿用本项目已记录的 **62 KiB 程序 + 2 KiB 设置**布局。Rust 对所有 BIN/HEX/ELF 数据段检查边界，禁止烧录覆盖 `0x0800F800`–`0x0800FFFF`；更新只擦写涉及的应用页并保留未覆盖字节，游戏机不提供整片擦除入口。完整 64 KiB 备份可读取和导出，但当前更新入口不接受直接回写含设置区的整片备份。若以后更换芯片或固件分区，需要同步修改产品配置和范围校验。

连接后核对 `DBGMCU_IDCODE` 系列 ID `0x410`，从 `0x1FFFF7E0` 读取实际容量并要求 64 KiB，从 `0x1FFFF7E8` 读取 96 位 UID。地址依据 [ST 官方 STM32F103xB 设备头](https://github.com/STMicroelectronics/cmsis-device-f1/blob/master/Include/stm32f103xb.h)，系列 ID 依据 [RM0008](https://www.st.com/resource/de/reference_manual/cd00171190.pdf)。容量不符、读保护或连接失败时报告错误；不自动解除读保护，也不尝试未标称的 128 KiB 区域。

操作期间锁定串口连接、演示启动、页面切换和返回产品库，复用全局固件任务锁与窗口关闭保护。成功或失败后恢复操作。读取数据在工作台页面间切换时保留；返回产品库或退出应用前请导出。浏览器预览禁用真实 ST-Link 操作。

## 本地固件检查

“存储与检查”页的独立检查工具接受从 **`0x08000000` 开始的原始 `.bin`**，该工具不解析 ELF、Intel HEX 或压缩包；“固件与 Flash”页支持上述 BIN/HEX/ELF/AXF 烧录。单次文件读取上限为 16 MiB，不能理解为设备可执行容量。

检查在主机本地完成，计算 IEEE CRC-32，并检查：

- 文件非空、具有至少 8 字节的初始向量，并且不超过当前 63,488 B 程序区；
- 小端初始栈指针位于 `(0x20000000, 0x20005000]`，按 8 字节对齐；
- 复位向量设置 Thumb 位，其目标位于当前映像内且不进入设置区。

这些检查只能排除明显的容量或向量错误。CRC-32 用于文件比对，不是签名或身份认证；向量合理也不能证明文件属于 GameBox、适合当前 OLED 接线、版本正确或可以安全执行。通过检查不会开放串口刷写，也不会把文件写入游戏机或外置 Flash。

当前内部 Flash 分配固定如下：

| 区域 | 地址范围（右端不含） | 容量 |
|---|---|---|
| 应用 | `0x08000000..0x0800F800` | 62 KiB / 63,488 B |
| 设置页 A | `0x0800F800..0x0800FC00` | 1 KiB |
| 设置页 B | `0x0800FC00..0x08010000` | 1 KiB |

审计时导出的 SPI Release `.bin` 为 **60,608 B**，剩余 **2,880 B**；I²C Release 为 **61,792 B**，剩余 **1,696 B**。依据为固件 `docs/instrument-validation.md:9` 及本地 `artifacts/firmware/gamebox-f103-{spi,i2c}.json`。两份 `.bin` 的 SHA-256 已与各自清单核对；数值仅代表这些构建，不是串口读取的设备占用信息。

固件仓库已有 `.bin/.elf/.hex/.json` 导出流程。JSON 清单记录显示接口、构建特征、目标、程序基址、设置保留范围、Flash/静态 SRAM 用量，以及每个文件的大小和 SHA-256；上位机可独立检查 `.bin` 或通过 SWD 烧录 `.bin/.elf/.hex`，尚未导入或验证该 JSON 清单。

## 后续规划：串口与外置 Flash

以下串口升级和外置存储能力均为设计规划；当前已实现的 ST-Link/SWD 烧录不依赖这些能力。具体 NOR 型号、容量、引脚、分区大小和协议编号需要随硬件与 bootloader 一起确定。

**第一阶段：版本化握手。** 固件增加 UART RX 后，先定义有界帧、协议 `major.minor`、请求标识、长度、超时和错误应答，再协商产品/硬件信息、固件版本与 capabilities。可分别描述按键观察、配置读写、存储查询、镜像传输、安装与启动能力；未协商的写能力保持不可用。旧 TX 固件继续只读，不自动向它发送未来命令。

**第二阶段：外置 Flash 固件包存储。** 用 NOR 存放多个固件包、包目录及必要资源。设备报告实际容量、擦除/写入粒度、可用槽位和单次传输上限；主机按包标识、序号、偏移及长度分块传输，使用块 CRC 检查传输错误，并在完整接收后核对预期文件 hash。明确哪些块已持久写入，重复传输应幂等，断线后查询进度并恢复。目录更新与“完整可用”标记最后提交，未完成包不得被选为启动来源。CRC 或 hash 单独都不提供来源认证，未来若需要验证发布方，需另行设计签名和信任根。

**第三阶段：引导安装与恢复。** 自定义 bootloader 在内部 Flash 常驻，将选中的完整固件包复制到内部应用区，安装前后验证边界及完整性，保留两个设置页。需要重新约定 bootloader、应用向量基址和应用上限，并在主机检查与链接脚本中同步；当前固定 `0x08000000` 的检查不能沿用到新的应用布局。安装进度需可恢复，外置存储保留完整来源及经过验证的恢复镜像；断电重启后只能继续安装或进入恢复流程，不能跳转到部分写入的应用。具体页级恢复策略、元数据冗余和失败回退必须通过断电测试确定。

**容量边界：普通 SPI NOR 不能扩展 F103 的直接代码执行空间。** STM32F103C8 的 SPI 是寄存器收发外设，不能直接从普通 SPI NOR 执行代码（XIP）。外置 Flash 可以保存多个镜像或数据，但选中镜像仍需装入内部可执行存储；采用上述内部 Flash 安装方案时，每个应用必须单独装得下。若 bootloader 占用内部 `B` 字节，保持设置区不变时应用理论上限不超过 `63,488 - B` 字节，实际还受页对齐与元数据安排影响。bootloader 会进一步压缩目前已经很紧的空间，需要裁剪/拆分游戏固件、把合适的资源移到外存，或更换更大容量的 MCU；不能通过外置 Flash 宣称单个现有大固件已突破内部容量限制。

上述 SPI 边界同时核对了本地 STMicroelectronics CMSIS 设备头：`Dummy-Robot/2.Firmware/Ctrl-Step-Driver-STM32F1-fw/Drivers/CMSIS/Device/ST/STM32F1xx/Include/stm32f103xb.h:462` 定义 SPI 控制、状态和数据寄存器，`:573`、`:575`、`:593`、`:611` 区分 Flash/SRAM 与 APB SPI 外设地址；该芯片定义没有 SPI NOR 的内存映射执行接口。审计副本位于 `C:\kk_data\code\github_clone`，仅作来源记录，不是本项目依赖。该头文件为 x8/xB 共用定义，不能用其中的 Flash bank 末地址推断本板 C8 有 128 KiB；本工程仍按已确认的 64 KiB 容量约束。

引脚也需复核：当前 PB12、PB13、PB14、PB15 已用于 Jump、Func、Enter、Back（固件 `README.md:84`），不能直接假定它们可作为 SPI2 接外存。SPI OLED 的 PA6 则是 D/C 信号；共享总线、MISO、片选和 DMA 的安排需要新的板级设计。

## 验证范围

上位机新增功能仍需与真实 USB-UART 和当前 GameBox 固件联调。无硬件演示、解析器测试和本地文件检查不能替代下列台架验证：

- 核对 115200 8N1、启动行、八键全部事件、设备复位及中途连接；
- 检查半行/多行、未知文本、连续数据、拔线重连与旧会话事件隔离；
- 从 WL1 切换到 GameBox，再断开返回产品库，确认端口和后台读取任务释放；
- 用实际 SPI/I²C `.bin` 与超限、损坏向量样本核对本地检查，确认检查过程没有串口写入。
- 用 ST-Link V2/V3 在 F103C8T6 上验证 BIN/HEX/ELF 烧录、回读校验与复位，更新前后对比末尾两个设置页，核对完整 64 KiB 备份及最后一个字节；检查断线、读保护拒绝、容量不符与复位下连接。

固件仓库已有的 GPIO/OLED/ADC/I²C 实机记录只证明其标明的固件与设备侧范围，没有验证本次新增的上位机串口链路。未来启用外置 Flash 或升级前，必须另行完成传输恢复、设置保留、错误镜像拒绝及逐阶段断电恢复验证。
